# Incident: Radar stuck on "Scanning airspace..." (2026-10-25)

**Status:** Fixed and live (commit `4fe53ba`, deployed 2026-10-25). Monitoring added in the follow-up commit.

## What users saw

`skyledger.org/flights` never loaded any aircraft. The radar stayed on
**"Scanning airspace..."**, and the bottom bar read **"0 of 0 aircraft shown"** and
**"Failed to fetch flights"**.

## Root cause (one sentence)

ADSB.lol, our live flight-data provider, started rejecting requests whose
`User-Agent` header is `node`. That's the default sent by Node's built-in
`fetch`, and our server code never set its own, so every flight request from
Vercel got **403 Forbidden**.

### How the failure chained

```
Browser /flights  ->  GET /api/flights/nearby  (our Vercel server)
                         -> fetch("https://api.adsb.lol/v2/lat/..")   User-Agent: node
                         <- 403 Forbidden
                      <- 502 {"error":"Failed to fetch flight data"}
Browser shows "Failed to fetch flights"; scan animation never finishes
```

### How we proved it

| Test | Result |
|---|---|
| `curl skyledger.org/api/flights/nearby?...` (live site) | **502** |
| `curl api.adsb.lol/...` from a laptop (curl sends its own User-Agent) | **200**, 31 aircraft |
| Same request with **no** User-Agent | **403** |
| Same request with `User-Agent: node` | **403** |
| Node `fetch()` exactly as our code called it | **403** |
| Node `fetch()` with `User-Agent: SkyLedger/1.0 (+https://skyledger.org)` | **200**, 31 aircraft |

The database was **not** involved. Supabase was confirmed healthy the same day
(see the keep-alive fix, commit `9be39ee`).

## Everything this broke (not just the radar)

All of these run through `src/lib/api/adsb.ts`, so all of them failed:

- **Radar** (`/flights`): no aircraft.
- **Aircraft detail and tail-number lookup** (`/api/flights/detail`, `/api/flights/lookup`): live position always missing. These failed **without any error showing**, returning "not found" instead.
- **Citizen report correlation** (`/api/correlate`): reports submitted during the outage got **no candidate pool** from live data.
- **Streak report correlation** (`lib/streak/correlate.ts`): live-snapshot source empty. The historical source still worked, but see below.
- **Flight history recording**: positions are only saved *by the radar in a visitor's browser* (`flight-layer.tsx`, every 60s). No radar data meant **no history was recorded** for flagged, known-operator, high-suspicion, or pinned aircraft. There is a gap in `flight_positions`.

### When did it start? (unknown, here's how to find out)

We don't know the start date. Run this in **Supabase → SQL Editor**:

```sql
-- Last time any flight position was recorded before the fix
select max(observed_at) as last_recorded_before_fix
from flight_positions
where observed_at < '2026-10-25';
```

That timestamp is roughly when the outage began. The data in the gap can't be
recovered: ADS-B history isn't something we can re-download.

## The fix (commit `4fe53ba`)

All in `src/lib/api/adsb.ts`:

1. **Explicit User-Agent on every request.** `SKYLEDGER_USER_AGENT` is sent on all ADSB.lol calls, plus the ADSB.lol route lookup in `adsbdb.ts`.
2. **Automatic backup provider.** If ADSB.lol fails (error status, network error, 8-second timeout, or garbage response), the same query is retried against **adsb.fi**, which serves the same data format. Users see aircraft either way.
3. **One retry on HTTP 429 (rate limited).** adsb.fi allows only 1 request/second.
4. **Loud logs.** Every provider failure is logged with `[flight-feed]` in Vercel logs, *even when the backup hides it from users*.
5. **Self-diagnosing API.** `/api/flights/nearby` now includes `"source": "adsb.lol"` or `"adsb.fi"`. When everything fails it returns each provider's HTTP status, so the browser's network tab shows exactly what broke.

Tested by simulating each failure (403, network error, 429, everything down) against the real code, plus a production build and a local server test before deploying.
After deploying, the live site returned 28 aircraft (`source: adsb.lol`).

### Backup options we considered

| Provider | Result |
|---|---|
| **adsb.fi** | ✅ Works, same format. **Chosen.** |
| airplanes.live | ❌ 403s our requests even with a User-Agent |
| OpenSky Network | Already used elsewhere, but needs OAuth credentials, has tight daily limits, and uses a different data format. Not worth it as a drop-in. |

### adsb.fi terms (must follow)

From [github.com/adsbfi/opendata](https://github.com/adsbfi/opendata):
- **1 request/second.** Fine as a backup, but it can't carry heavy traffic for long. That's why the monitor alerts when the *primary* is down, even while the backup is working.
- **Personal, non-commercial use only.** If SkyLedger ever charges money, revisit this.
- **Must credit adsb.fi with a link.** Done on `/flights` ("How flight tracking works") and `/about` (Data Sources).

## Making sure we hear about it next time

The real failure was that **nothing told anyone**. Three layers now:

| Layer | What it does | Catches it within |
|---|---|---|
| **Backup provider** | Keeps the radar working if ADSB.lol fails | Immediately (users don't notice) |
| **`/api/health`** + an uptime monitor | Public status check: tests both flight feeds and the database. Returns **HTTP 503** if the primary feed or the database is down | **5 minutes**, once the monitor below is set up |
| **Daily email** (`/api/cron/health-check`, Vercel Cron 13:00 UTC / 8am Central) | Runs the same checks and **emails ADMIN_EMAIL** if anything is degraded or down. Silent when healthy | 24 hours |

We used **Vercel Cron, not GitHub Actions**, for the daily check. GitHub silently
disables scheduled workflows on repos with no activity for 60 days. That's what
killed the Supabase keep-alive in September.

### ⚠️ Rex: two 5-minute setup steps

**1. Set up the free uptime monitor**
1. Sign up at [uptimerobot.com](https://uptimerobot.com) (free plan).
2. **+ New monitor** → type **HTTP(s)**.
3. URL: `https://skyledger.org/api/health`
4. Interval: **5 minutes**. Alert contact: your email (and the phone app if you want push notifications).
5. Save. It emails you whenever `/api/health` returns an error, and again when it recovers.

**2. Confirm the alert email actually reaches you** (once)
In a terminal, with `CRON_SECRET` from Vercel → Settings → Environment Variables:
```bash
curl -H "Authorization: Bearer YOUR_CRON_SECRET" "https://skyledger.org/api/cron/health-check?test=1"
```
You should get an email titled `[SkyLedger] ...` within a minute. `"emailed": true`
in the response means it was sent.

## Runbook: "the radar is broken again"

1. Open **https://skyledger.org/api/health** in a browser.
   - `flight_feed.providers` shows each feed's `ok` / `status` / `error`.
   - `serving: null` means both feeds are failing. Otherwise the site is up on whichever feed is listed.
2. If a feed shows **HTTP 403**, it's blocking us. Check whether it changed its rules
   (User-Agent, API key requirement, IP blocks). Check its site, GitHub, or Discord.
   ADSB.lol: <https://api.adsb.lol>. adsb.fi: <https://github.com/adsbfi/opendata>.
3. If a feed shows **429**, we're being rate limited. Usually temporary.
4. If a feed **times out**, the provider is probably down. The backup should cover it.
5. `database.ok: false` → Supabase (see the keep-alive notes in `private/OPS.md`).
6. Vercel → Project **openskies** → Logs, search `[flight-feed]`, for the history of failures.
7. To add another backup feed, add one entry to the `PROVIDERS` array in `src/lib/api/adsb.ts`.
   Any ADSBexchange-v2-compatible API works.
